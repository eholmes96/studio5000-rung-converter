# Studio 5000 Neutral ⇄ ASCII Rung Converter

A Windows desktop tool that converts Rockwell Studio 5000 / Logix Designer ladder logic
between **Neutral Text** and **ASCII** rung representations, in both directions, with live
auto-detection, an IDE-style rung gutter, and find & replace.

Python 3.11+ / Tkinter (standard library only). No external dependencies, no network
access, no telemetry.

---

## The two formats

| | Example |
|---|---|
| **Neutral text** | `XIC(a)XIO(b)OTE(c);` |
| **ASCII** | `SOR XIC a XIO b OTE c EOR` |

| Neutral | ASCII |
|---|---|
| rung start (implicit) | `SOR` |
| `;` | `EOR` |
| `[` | `BST` |
| `,` (branch-leg separator) | `NXB` |
| `]` | `BND` |
| `MNEMONIC(a,b)` | `MNEMONIC a b` |
| `MNEMONIC()` | `MNEMONIC` |
| operand containing spaces | `"quoted operand"` |

---

## ⚠ The single-line rule — the whole point of this tool

**Studio treats every newline in pasted text as a rung break.** A line break between rungs
injects a spurious empty rung into your routine.

So:

- The two panes **display** one rung per line, purely so the gutter can number them.
- **Copy to clipboard and Save always emit a single line with no newline characters.**
  The per-line layout you see on screen is never what gets copied.
- Saved files are written **without a trailing newline**, for the same reason — a trailing
  newline gets selected along with the text and becomes an empty rung on paste-back.

The buttons are labelled `Copy output (Studio-safe, 1 line)` and `Copy input (1 line)` to
make this explicit.

On input, newlines are treated as insignificant whitespace. Rung boundaries come only from
tokens: a rung ends at `EOR` **or** at the next `SOR`, whichever comes first, so a missing
`EOR` does not merge two rungs.

## Running it

```bash
python converter.py
```

Tests — two suites, both exit 0 on success and 1 on any failure:

```bash
python converter.py --selftest
```

Parser and emitters: round-trips, branch handling, expression quoting, v36 mnemonics,
highlighting spans. Also available in the GUI under **Help → Run self-test (dev)** or
**Ctrl+Alt+T**.

```bash
python test_gui.py
```

The Tkinter layer: panes, rung gutter, find & replace, history dropdowns, highlight-all,
double-click selection, Alt accelerators, syntax colouring and its settings file, and the
failure paths. It builds the real application and drives it — a window will flash on screen
for a second or two, which is expected. Nothing is mocked.

## Building the standalone .exe

PyInstaller is not required to run the script — only to produce the redistributable
`.exe`. Install it once:

```bash
pip install pyinstaller
```

Then build:

```bash
python -m PyInstaller --noconfirm --noupx --onefile --windowed --name Studio5000RungConverter converter.py
```

The result is `dist\Studio5000RungConverter.exe` — a single ~11 MB file that runs on
Windows 10/11 with no Python installation on the target machine. This is the exact command
used to produce the shipped build. `--noconfirm` lets it overwrite the previous build in
place. `--noupx` stops PyInstaller from compressing the exe with UPX if UPX happens to be
installed; UPX-packed executables draw more antivirus false positives.

PyInstaller also leaves a `build\` folder and a `Studio5000RungConverter.spec` file. Both
are generated by the command above on every build and are safe to delete; change build
options in the command, not in the spec.

### Self-test from the .exe

`--windowed` means the executable has no stdout, so the self-test would otherwise run
silently. The app re-attaches to the console that launched it, so this works and reports
normally:

```bash
dist\Studio5000RungConverter.exe --selftest
```

Double-clicked with no console attached, it still runs and still sets the exit code — you
just won't see the text. Use **Help → Run self-test (dev)** in the GUI for that case.

### Distributing it

An unsigned PyInstaller `--onefile` executable will usually trip Windows SmartScreen
("Windows protected your PC") on first run on another machine, and some corporate
antivirus products flag the PyInstaller bootloader heuristically. Both are expected for an
unsigned single-file build, not a sign of a problem with the tool. Code-signing the .exe is
the clean fix if you plan to hand it around widely.

## Using it

| Control | What it does |
|---|---|
| **Input pane** (left) | Paste or type here. Conversion is live, debounced ~250 ms. |
| **Output pane** (right) | Read-only result in the other format. |
| Detection label | Reads `Neutral detected` / `ASCII detected`, `—` when empty, `Unrecognized` when neither. |
| **⇄ Swap** | Moves the output into the input and re-converts, so you can chain conversions. |
| **Format rungs** | Re-lays the input out as one rung per line. Runs automatically on paste and on file load. |
| **Word wrap** | **On by default.** Toggles wrapping in both panes; the gutter still numbers one entry per rung. |
| **Sync scroll** | Locks the two panes' vertical scrolling together. |
| **Find & Replace** | Open by default. Ctrl+F / Ctrl+H focuses the Find field; Esc hides the bar. |
| **Load file…** | Opens a text file, or a Studio rung scrap (`.shs`) with its rung comments. |
| **Save .shs for Studio…** | Saves the rungs *and their comments* as a `.shs` file to drag into a Studio routine. See [Keeping rung comments](#keeping-rung-comments). |

The gutter numbers **rungs starting at 0**, matching Studio's own rung numbering.

### Double-click selects one token, not the whole rung

Tcl on Windows defines a "word" as any run of non-whitespace. Neutral text has no
whitespace at all, so Tk's own double-click would select an entire rung. Double-click is
therefore handled directly, splitting on:

```
space  (  )  [  ]  ,  ;  "  '
```

**`.` and `:` are deliberately not delimiters**, so a dotted member path or a module address
selects as one unit — double-clicking anywhere in `_Drive1:I.OutputCurrent` grabs all of it.

Square brackets *are* delimiters, as requested, which means a subscripted tag selects in
three pieces:

| Double-click on | Selects |
|---|---|
| `SafetyZone[2].QuickStopOK` (base) | `SafetyZone` |
| the `2` | `2` |
| `QuickStopOK` | `.QuickStopOK` |
| `_Drive1:I.Ready` (anywhere) | `_Drive1:I.Ready` |

If you would rather a subscripted tag selected whole, remove `[` and `]` from
`WORD_DELIMITERS` at the top of `converter.py` — one line.

Clicking directly on a bracket, paren or comma selects just that character. Triple-click
still selects the whole line, which is the whole rung.

### Syntax colours

Both panes are syntax-highlighted. Colouring is driven by the parser, not by pattern
matching, so it reflects how the text will actually be *converted* — which is what makes
the AOI category possible.

| Category | Covers | Default |
|---|---|---|
| Rung | `SOR` `EOR` `;` | gray `#5F5E5A` |
| Branch | `BST` `NXB` `BND` `[` `,` `]` | purple `#534AB7` |
| Instruction | every known mnemonic, compute included | blue `#185FA5` |
| AOI / unknown | mnemonic not in the known set | red `#A32D2D` |
| Raw value | `5000`, `16#000F`, `'text'` | green `#3B6D11` |
| Quoted expression | the `CPT`/`CMP`/`FAL`/`FSC` expression | amber `#854F0B` |
| Rung comment | a `//` comment line above its rung | dark green `#1B5E20` |

Tags and ordinary operands are deliberately **not** coloured — they use the pane's normal
text colour. On a 200-rung routine that restraint is what keeps the highlighting readable.

**The AOI colour earns its place.** With `AOI_INSTRUCTIONS` empty, ASCII → Neutral silently
folds a tag-shaped AOI name into the preceding instruction. Red makes that visible in the
pane before you paste anything back into Studio — the one category that turns a silent
failure into an obvious one.

**Changing them:** *View → Syntax colours…* Click a swatch for the colour picker, or type a
hex value directly. Changes apply live to both panes. "Reset to defaults" restores the
table above.

Your palette is saved to `%APPDATA%\Studio5000RungConverter\settings.json` and reloaded on
start. If that file is missing, unreadable, or contains a bad colour, the defaults are used
— a corrupt settings file can't stop the app from launching.

Highlighting is display only. Copy and Save emit exactly the same plain single-line text
they always did.

### Why the input pane doesn't reformat while you type

Reformatting on every keystroke would move the caret out from under you. The input pane is
re-laid-out on **paste**, on **file load**, on **Swap**, and when you press **Format
rungs** — which covers the normal workflow of pasting a blob out of Studio. While you are
typing freely, the gutter is showing plain 0-based line numbers.

### Find & Replace

Operates on the **input pane only**; the output updates indirectly through the normal
conversion path. Fields: Find, Replace. Buttons: Find next, Replace, Replace all, with a
live match counter. Checkboxes: **Case-sensitive**, **Whole word** (match bounded by
non-word characters; plain substring otherwise), and **Include comments**.

**Include comments** (off by default). Off, Find & Replace skips the `//` comment lines
entirely: they are not counted, highlighted, found or replaced, so renaming a tag changes
only the logic. Tick it to search and replace inside comments as well.

**Highlight all** (on by default, leftmost checkbox). Every occurrence of the find term gets
a grey background; the **active** match keeps the normal blue selection. So you can see at a
glance that a tag appears five times, while still knowing which one **Replace** will act on
— Replace only ever touches the blue one.

Highlighting greys the matches in both panes; the blue active match and every edit stay
in the input pane.

**History dropdowns.** Both fields remember what you've used, Excel-style:

- **Down arrow** in the field opens the list.
- **Up / Down** move through it, **Enter** picks the highlighted entry, **Esc** dismisses.
- Most recent first; re-using a term moves it back to the top instead of duplicating it.
- Capped at 20 entries each. A term is recorded when you actually run Find next, Replace,
  or Replace all — not on every keystroke.

History lives for the session only; it is not written to disk.

## Keeping rung comments

Studio's **Ctrl+C puts no rung comments on the clipboard**, only the logic as plain text,
so pasting rungs in and out loses every comment. Studio's *rung scrap file* does carry
them, and Studio makes one whenever you drag rungs out of a routine.

1. In Studio, select the rungs and **drag them onto the desktop** (or into any folder).
   Studio creates a file named like `RSLogix 5000 RLL Scrap 'XIC(...'.shs`.
2. In the converter, **Load file…** and pick that `.shs`. Each rung appears on its own
   line with its comment above it, in dark green, as lines starting with `//`.
3. Edit as usual. Find & Replace leaves the comments alone unless you tick
   **Include comments**.
4. **Save .shs for Studio…**, then **drag the saved file into the routine** in Studio.
   The rungs are inserted with their comments.

How comment lines work in the panes:

- A comment line is a whole line starting with `//` (spaces before it are fine). `//`
  after logic on the same line is not a comment.
- A comment belongs to the rung directly **below** it, the next logic after it. Lines you
  type yourself follow the same rule, so you can add, edit or delete comments in the pane.
- A comment after the last rung belongs to no rung. It raises a warning and is left out of
  the saved file.
- A Studio comment that ends in a line break shows as a final empty `//` line. It is kept
  so the comment goes back exactly as it came.
- **Copy output**, **Copy input** and **Save output…** never include comments; plain text
  has nowhere to put them. Only **Save .shs** carries them, always as Neutral text, even if
  the input pane holds ASCII. **⇄ Swap** keeps the comments.
- The gutter numbers rungs only, so the numbers still match Studio's.

## Expression operands (CPT, CMP, FAL, FSC)

ASCII is space-delimited, but a compute expression contains spaces:

```
CPT(Drive1.Status.Current,_Drive1:I.OutputCurrent / (Drive1.Config.MotorFLA *100));
```

Written bare, that expression would shatter into four meaningless tokens. Studio wraps it
in double quotes so it stays one token, and so does this tool:

```
CPT Drive1.Status.Current "_Drive1:I.OutputCurrent / (Drive1.Config.MotorFLA *100)"
```

Four instructions take an `expression` operand, per the RM014 table, and all four are
handled:

| Instruction | Neutral text format |
|---|---|
| `CMP` | `CMP(expression)` |
| `CPT` | `CPT(destination,expression)` |
| `FSC` | `FSC(control,length,position,mode,expression)` |
| `FAL` | `FAL(control,length,position,mode,destination,expression)` |

**The rule is "quote when needed":** an operand is quoted if and only if it contains
whitespace. A space-free expression such as `(A+B)*C` is unambiguous as a single token and
is left bare, so no quotes are introduced that Studio didn't ask for. The same rule covers
string literals — `MOV('hello world',Dest)` now round-trips too.

Reading ASCII back, a quoted run is always one operand and is never mistaken for an
instruction. If an expression arrives **unquoted** — hand-written, or produced by an older
build of this tool — it is re-assembled rather than shattered, because the expression is
always the final parameter of those four instructions. That recovery collapses runs of
whitespace inside the expression to single spaces, and says so in the warning banner.

This is also why `FAL`/`FSC` mode operands like `ALL` and `INC` are read correctly: they
sit inside the instruction's guaranteed operand prefix, so they are treated as operands
even though they are shaped exactly like mnemonics.

## Adding your Add-On Instructions (AOIs)

Open `converter.py` and add your AOI names to the list at the top of the file:

```python
AOI_INSTRUCTIONS: list[str] = [
    "Example_Aoi_1",
    "Example_Aoi_2",
]
```

**The list ships empty on purpose.** The tool knows only the standard Rockwell instruction
set, so no site-specific AOI names are baked into the file — add your own locally and they
stay local.

Anything listed there is treated as an instruction with no warning. This only affects the
**ASCII → Neutral** direction — see below.

**This is not cosmetic.** An AOI whose name is shaped like a tag — underscores and
lowercase, e.g. `Example_Aoi_1` — is otherwise classified as an *operand* and folded into
the preceding instruction:

```
XIC(Tank_Enable)Example_Aoi_1(A,B)   →  becomes  →  XIC(Tank_Enable,Example_Aoi_1,A,B)
```

**And it happens silently** — the tool has no way to know it guessed wrong, so a mangled
rung looks perfectly clean with no warning. That is the reason to fill the list in.
Registering the name fixes the round-trip exactly.

Neutral → ASCII is unaffected either way, because the parentheses already say it's an
instruction. If you only ever convert Neutral → ASCII, this list does nothing for you.

An AOI with a short all-caps name converts correctly without being registered, because the
shape heuristic catches it — but it raises the "Unrecognized instruction(s)" banner on
every conversion until you add it. Those are noise; tag-shaped names are the dangerous
ones.

The built-in `KNOWN_INSTRUCTIONS` list immediately above it holds the 199 standard relay
ladder mnemonics and is also editable if you need to correct or extend it. Alongside it,
`V36_MNEMONIC_UPDATES` carries the 16 instructions renamed in Logix Designer v36 — 215
mnemonics recognized in total. See below.

## How the two directions differ

**Neutral → ASCII is unambiguous.** Parentheses fully define operand grouping, so this
direction consults no instruction table at all and works for any instruction or AOI,
known or not.

**ASCII → Neutral is inferred.** ASCII tokens are space-separated, so the instruction /
operand boundary has to be guessed:

1. Structural keywords `SOR EOR BST NXB BND` are recognized explicitly.
2. A token in the built-in instruction set is a mnemonic. **The set is authoritative.**
3. Otherwise the shape heuristic applies as a fallback: a short all-caps token
   (`^[A-Z]{2,4}[0-9]?$`) is a mnemonic; anything containing `.` `[` `:` `_`, a digit, or
   lowercase, or longer than 4 characters, is an operand.
4. A mnemonic **greedily consumes** following operand tokens until the next mnemonic or
   structural keyword. This handles variable arity automatically — `XIC` takes 1, `OSF`
   takes 2, `NOP` takes 0 — with no hard-coded operand counts.

Anything that can't be classified confidently is still converted and never dropped, but is
collected into the warning banner: *"Unrecognized instruction(s): X, Y — verify output."*

## Sources

The format and the instruction set are taken from Rockwell's own documentation, not
inferred from the sample:

- **Logix 5000 Controllers Import/Export Reference Manual, publication 1756-RM014D-EN-P
  (September 2025)** — Chapter 9, *Define a ladder logic routine*.
  - The branch examples on p. 210 and the rung-termination syntax.
  - The **"Neutral text for ladder instructions"** table, pp. 210–221, which is the source
    of all 199 mnemonics in `KNOWN_INSTRUCTIONS`. That table spans the general instructions
    (1756-RM003 / 1756-RM018), the process & drives instructions (1756-RM006), the safety
    instructions, and the motion instructions (MOTION-RM002, formerly 1756-RM007).
  - The control-character escape table on p. 40.

### Logix v36 renamed 16 instructions

In Logix Designer v36, 16 mnemonics were changed to conform to IEC 61131-3 and PLCopen.
Studio v36+ emits the **new** spelling when you copy rungs; older projects and exports carry
the legacy one.

| Instruction | v35 and earlier | v36 and later |
|---|---|---|
| Arc cosine | `ACS` | `ACOS` |
| Arc sine | `ASN` | `ASIN` |
| Arc tangent | `ATN` | `ATAN` |
| Convert to BCD | `TOD` | `TO_BCD` |
| Convert to integer | `FRD` | `BCD_TO` |
| Equal to | `EQU` | `EQ` |
| Greater than | `GRT` | `GT` |
| Greater than or equal to | `GEQ` | `GE` |
| Less than or equal to | `LEQ` | `LE` |
| Less than | `LES` | `LT` |
| Limit | `LIM` | `LIMIT` |
| Move | `MOV` | `MOVE` |
| Not equal to | `NEQ` | `NE` |
| Square root | `SQR` | `SQRT` |
| Truncate | `TRN` | `TRUNC` |
| X to the power of Y | `XPY` | `EXPT` |

Source: Studio 5000 Logix Designer online help, *Instruction Set → Updated instruction
mnemonics*.

**Both spellings are recognized, and neither is ever rewritten.** The converter reproduces
whichever spelling you gave it, so a v36 paste stays v36 and a legacy export stays legacy.
It will not silently modernize your logic — if you need one converted to the other, that is
a find-and-replace, deliberately.

Four of the new names — `LIMIT`, `TRUNC`, `TO_BCD` and `BCD_TO` — are longer than four
characters or contain an underscore, so the shape heuristic reads them as *operands*.
Before they were added to the known set, ASCII → Neutral silently folded them into the
preceding instruction. The other twelve merely raised the "Unrecognized instruction(s)"
banner.

**Documentation conflict, flagged as required.** `KNOWN_INSTRUCTIONS` is extracted from the
1756-RM014D-EN-P neutral-text table (September 2025, import/export version 2.29 for Logix
Designer v38) — and that table still lists **only** the legacy spellings, even though the
rename landed two releases earlier in v36. The online help is correct and the manual is
stale, so the v36 names are carried in a separate `V36_MNEMONIC_UPDATES` map rather than
being merged into the RM014-derived list. That keeps each list traceable to its own source.

### Studio rung scrap files (`.shs`)

Not documented by Rockwell. The layout was worked out from files Studio itself made:

- A fixed 40-byte header: an MFC class record for `CScrapFileHeader`, then the
  length-prefixed UTF-16 string `rungs`.
- UTF-16LE text with one entry per LF: `RG: <neutral text>;` is a rung, and `RC: <comment>`
  is the comment of the rung *before* it. Line breaks inside a comment are CR LF. There are
  no counts, lengths or checksums.
- Studio writes the whole file in C text mode, so every `0x0A` byte is stored as
  `0x0D 0x0A`. The tool undoes that when reading and repeats it when writing.

Checked in Studio on 2026-10-29: a real file rebuilt byte for byte by the same code, then a
copy with one comment edited, then a copy with a tag renamed, were each dragged back into a
routine and inserted correctly. Those files were made by a script using the format code;
a file written by the app's own **Save .shs** button has not yet been dragged into Studio.
Studio's Ctrl+C was checked the same day: the clipboard held only plain text and a picture.

### Spec vs. sample: the branch discrepancy

**The manual and the working sample encode branches differently, and the tool accepts
both.**

RM014's own L5K examples put a comma immediately after the opening bracket (p. 210):

```
N: XIC(conveyor_a)[,XIC(input_1) XIO(input_2) ]OTE(light_1);
N: XIC(conveyor_b)[,XIC(input_1) XIO(input_2) ,XIC(input_a) XIO(input_b)  ]OTE(light_2);
```

That leading comma means the branch's **first leg is empty** — a straight pass-through
wire around the instructions in the other leg(s). It is not a syntactic requirement of `[`.

Real Studio copy/paste output, including the canonical sample this tool was built against,
writes branches with no leading comma when no pass-through leg exists:

```
[XIC(a)XIC(b),XIC(c)XIC(d)]OTE(e);
```

Both are handled by the same stack-based parser and both round-trip losslessly. An empty
leg becomes an adjacent `BST NXB` (or `NXB BND`) pair in ASCII, which is the faithful
representation. Both forms are covered by the self-test.

### String operands and the `$` escape

RM014 p. 40 defines `$` as the escape character inside Logix string literals: `$$` for a
literal `$`, `$'` for a quote, `$Q`, `$L`/`$N`/`$P`/`$R`/`$T` for control characters, and
`$xxxx` for a hex character code. The neutral-text scanner honours this, so a `,` `)` `[`
or `]` inside a `'quoted string'` operand is preserved verbatim rather than treated as
structure.

## When a conversion fails

If the input can't be converted, the tool **clears the output rather than leaving the
previous result on screen**. You get a red banner naming the cause, the detection label
reads "Conversion failed", and Copy refuses with an explanation instead of handing over
rungs from an earlier input.

That matters more than it sounds: Tkinter silently swallows exceptions raised inside
scheduled callbacks, so without this the panes would keep showing the *last successful*
conversion with no sign anything had gone wrong — and Copy would put those stale rungs on
your clipboard.

**Branch nesting is capped at 100 levels.** The emitters recurse once per level, so
unbounded nesting would exhaust Python's stack mid-conversion. Real ladder never comes
close — Studio's own limit is far lower — so anything past the cap is refused with a clear
message. The realistic trigger is picking the wrong file, not real logic.

## Known limitations

- **ASCII → Neutral inference caveat.** A tag whose name is spelled exactly like an
  instruction mnemonic (e.g. a BOOL literally named `ESTOP` or `MOV`) will be read as an
  instruction, because the ASCII format genuinely does not distinguish them. Neutral →
  ASCII is unaffected. If you hit this, the fix is to rename the tag or edit the affected
  rung by hand.

- **An operand containing both a space and a double-quote character cannot be represented
  in ASCII.** Quoting is the mechanism that protects spaces, so an embedded `"` has nothing
  left to escape it — no escape convention for this is documented by Rockwell, and
  inventing one risked producing text Studio would reject. The tool warns and names the
  rung rather than failing silently. Logix string literals use single quotes, so this
  should not arise in practice.

- **Rung comments need a `.shs` file.** Studio's plain-text copy has none, so comments only
  come through [Keeping rung comments](#keeping-rung-comments). Stray non-logic text is
  passed through untouched and raises a soft warning rather than crashing.

- **Only rung comments.** Instruction and operand descriptions are not carried.

- **Ladder (RLL) only.** Structured Text, Function Block Diagram and SFC are not supported.

- **One trailing empty rung is stripped.** Studio appends the routine's END rung when you
  copy a whole routine, and you don't want it re-inserted on paste-back. A *non-trailing*
  empty rung is always preserved, and only one trailing empty rung is ever removed.

## What the self-test covers

`python converter.py --selftest` runs 42 conversion checks plus format detection,
newline-free output, and AOI passthrough:

- Both directions against the canonical paired fixture (a real safety routine, with the
  tag names changed).
- Both round-trips: Neutral → ASCII → Neutral and ASCII → Neutral → ASCII.
- **Nested branches** (`[ … [ … ] … ]` ⇄ `BST … BST … BND … BND`), including a
  branch-as-first-element case. The canonical sample has none, so these are purpose-built.
- **Noisy input normalization**: first rung with no leading `SOR`, a rung *missing its
  `EOR`* that runs straight into the next `SOR`, and stray double spaces — all normalizing
  to the canonical single-line output.
- **Newlines between rungs** are stripped on input and never emitted.
- Raw Studio copy with inter-rung spaces and a trailing empty END rung.
- Empty rungs: mid-routine preserved, exactly one trailing rung dropped.
- Bracket/paren/comma disambiguation: `MOV(Array[1,2],Dest[3].Sub)`, `EQU(Tag[Idx[0]],7)`,
  `CPT(Dest,(A+B)*C)`.
- **Expression operands with spaces**, both directions and round-trip, using two `CPT` rungs
  adapted from a real drive routine (tag names changed), plus `CMP`, `FAL` and `FSC` — including `FAL`/`FSC` mode
  operands (`ALL`, `INC`) that are shaped like mnemonics.
- Unquoted expressions on input are re-assembled, not shattered.
- A quoted operand is never classified as a mnemonic (`CPT Dest "MOV + XIC"`).
- A string literal containing spaces round-trips.
- **Syntax highlighting spans** land on exactly the right substrings in both formats, never
  run past the end of their display line, and classify radix and string literals as raw
  values while leaving tags uncoloured.
- **Logix v36 mnemonics**: all 32 spellings (16 legacy + 16 renamed) classify as
  instructions and raise no warning; `LIMIT`, `TRUNC`, `TO_BCD` and `BCD_TO` are asserted
  not to be folded into the preceding instruction; both spellings convert side by side.
- Zero-operand instructions (`NOP()AFI()TND();`).
- RM014's leading-comma branch form.
- Detection, including keyword-shaped tags inside operands (`XIC(SOR)OTE(BND);` is
  correctly read as Neutral, not ASCII).
- **Rung comments and `.shs` files**: a scrap file laid out as Studio writes one (text-mode
  `0x0D 0x0A` included) reads into the right rungs and comments, and rebuilds byte for byte,
  directly, through the pane and through the ASCII side. Comments attach to the rung after
  them, even after a missing `EOR`; never leak into the single-line output; never decide the
  detected format; and a commented empty last rung is kept.

`python test_gui.py` adds the GUI side: loading a `.shs`, dark-green comment lines in both
panes, a gutter that skips them, Include comments on and off for counting, highlighting,
Find next, Replace and Replace all, and saving back byte for byte from either format.

Any round-trip mismatch is reported as a failure with a character-level diff.
